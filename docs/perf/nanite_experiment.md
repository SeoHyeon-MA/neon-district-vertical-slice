# Nanite vs 전통 LOD — 원경 최적화 비교 실험 설계

기준선 측정에서 드로우 콜이 전 카메라 23으로 동일하게 나왔다. 템플릿 메시가 Nanite라
지오메트리가 전통적인 드로우 콜을 쓰지 않기 때문이다. 포트폴리오에 "드로우 콜 전후 비교"를
넣으려면 비교 대상이 되는 **비Nanite 경로를 따로 만들어야 한다.**

이 문서는 그 실험을 어떻게 설계하고, 그 결정이 Phase 2 키트 제작에 무엇을 요구하는지 정의한다.

---

## 1. 이 실험이 답하려는 질문

> 150m 플레이 구역을 둘러싼 원경 도시를, Nanite로 렌더링하는 것과
> 전통적인 LOD + 인스턴싱 + 컬링으로 렌더링하는 것 중 무엇이 이 씬에서 더 싼가.
> 그리고 그 차이는 어디에서 오는가.

"Nanite가 항상 빠르다" 또는 "HLOD를 켜면 좋아진다"는 결론은 의미가 없다.
**어떤 조건에서 어느 쪽이 유리하고, 그 이유가 무엇인지**를 수치로 보이는 것이 목표다.

---

## 2. 먼저 알아야 할 함정

### `r.Nanite 0`은 비Nanite 경로가 아니다

`r.Nanite 0`은 Nanite를 끄고 각 메시의 **폴백 메시(fallback mesh)** 로 그린다.
폴백 메시는 임포트 시 자동 생성된 단순화 결과물이지, 사람이 만든 LOD 체인이 아니다.
이걸로 잰 수치를 "전통 LOD 방식"이라고 제시하면 비교가 성립하지 않는다.

`r.Nanite 0`은 **Nanite 런타임 비용의 크기를 확인하는 용도**로만 쓰고,
비교 대상인 B안은 별도로 LOD를 만들어 구성한다.

### 스텁 큐브로는 아무것도 증명할 수 없다

현재 원경은 머티리얼 한 장짜리 큐브 20개다. 카메라 간 차이가 1ms에 불과하다.
이 상태에서 Nanite를 끄든 켜든 차이는 측정 노이즈에 묻힌다.

**실험은 충분히 무거운 콘텐츠 위에서만 유효하다.** 목표 밀도는 아래 3절에 정의한다.

### Nanite와 VSM은 붙어 있다

Nanite 지오메트리는 Virtual Shadow Map에 효율적으로 들어간다. Nanite를 끄면
그림자 패스 비용이 함께 변한다. 이건 결함이 아니라 **결과의 일부**이므로,
GPU 시간을 총합만 보지 말고 ShadowDepths 패스를 분리해 기록한다.

### 마스크드/반투명은 따로 잰다

네온 간판, 철망, 유리는 Nanite에 불리하다. 이 요소들을 원경 건물과 섞어서 재면
원인 분리가 안 된다. 간판류는 별도 측정 축으로 떼어낸다.

---

## 3. Phase 2 키트 제작에 대한 요구사항

이 실험을 하려면 키트를 만들 때부터 두 경로를 염두에 둬야 한다. 나중에 붙일 수 없다.

| 항목 | 요구사항 | 이유 |
|---|---|---|
| 건물 메시 폴리곤 | LOD0 기준 **2만 ~ 6만 삼각형** | 너무 가벼우면 Nanite의 장점도 LOD의 장점도 드러나지 않는다 |
| LOD 체인 | LOD0 / LOD1(50%) / LOD2(20%) / LOD3(5%) 수동 생성 | B안의 비교 대상. 자동 폴백 메시로 대체하지 않는다 |
| 머티리얼 | Opaque 마스터 1개로 통일, 파라미터만 변형 | 머티리얼 개수가 변수로 끼어들지 않게 한다 |
| 간판/철망/유리 | 별도 메시로 분리, 별도 태그 | 마스크드/반투명 축을 독립 측정 |
| 원경 배치 밀도 | Ring 1 + Ring 2 합쳐 **건물 인스턴스 300개 이상** | 차이가 노이즈 위로 올라오는 최소 규모 |
| 소스 관리 | 메시 에셋은 **한 벌만** 유지 | 두 벌로 복제하면 관리가 어긋난다 |

에셋을 두 벌로 복제하지 않고, 측정 직전에 스크립트로 Nanite 플래그와 LOD 설정을 전환한다.
전환 스크립트는 재현성을 위해 저장소에 남긴다.

## 4. 측정 구성 (Configuration)

한 번에 하나의 변수만 바꾼다. 각 구성은 앞 구성에서 **한 가지만** 다르다.

| ID | Nanite | LOD | 배치 | HLOD | Cull | 목적 |
|---|---|---|---|---|---|---|
| `C0` | 켬 | – | 개별 액터 | 끔 | 끔 | Nanite 기본선 |
| `C1` | 켬 | – | 개별 액터 | **켬** | 끔 | Nanite에서 HLOD의 기여 |
| `C2` | **끔** | LOD0–3 | 개별 액터 | 끔 | 끔 | 전통 방식 기본선 |
| `C3` | 끔 | LOD0–3 | **HISM** | 끔 | 끔 | 인스턴싱의 기여 |
| `C4` | 끔 | LOD0–3 | HISM | **켬** | 끔 | 전통 방식 + HLOD |
| `C5` | 끔 | LOD0–3 | HISM | 켬 | **켬** | 전통 방식 최종 |

추가 축 (본 매트릭스와 분리해 별도 기록):

- `S0/S1` — 간판(마스크드·반투명) Nanite 켬/끔
- `N0` — `C0` 상태에서 `r.Nanite 0`. **Nanite 런타임 비용 자체**를 보는 참고값이며
  `C2`와 같은 것으로 취급하지 않는다

카메라 5개 × 구성 6개 = 30회 실행. 실행당 약 90초이므로 한 번의 스윕에 45분 정도 걸린다.

## 6. 기록할 지표

| 지표 | 출처 | 무엇을 말해주는가 |
|---|---|---|
| GPU (ms) | CSV `GPUTime` | **주 지표.** GPU 바운드이므로 사실상 이것이 결론이다 |
| Frame / Render / Game (ms) | CSV | 병목이 GPU에서 CPU로 옮겨갔는지 확인 |
| DrawCall/BasePass | CSV | 인스턴싱과 HLOD의 직접 효과 |
| DrawCall/ShadowDepths | CSV | Nanite ↔ VSM 상호작용 |
| 삼각형 수 | `stat rhi` / Nanite 시각화 | 실제로 무엇이 줄었는지 |
| VRAM | `stat unit` / CSV | Nanite 스트리밍 풀 vs LOD 메시 메모리 |
| HLOD 빌드 시간 | 빌드 로그 | 최적화의 제작 비용 |
| 패키지 크기 | 쿡 결과 | 프록시 메시가 디스크에 미치는 영향 |

**노이즈 기준**: 기준선에서 같은 실행 내 median과 mean의 차이는 0.05ms 수준이었다.
다만 실행 간 편차는 아직 모른다. 각 구성을 **2회 이상 실행**하고, 두 회차의 차이가
0.2ms를 넘으면 3회차를 추가한다. **0.2ms 미만의 차이는 결론으로 쓰지 않는다.**

## 7. 예상 결과와 해석 방향

미리 예상을 적어두고 실제 결과와 대조하는 것 자체가 기록의 가치를 만든다.

| 예상 | 근거 |
|---|---|
| `C0` vs `C2`에서 Nanite가 삼각형 수에 둔감 | Nanite는 화면 픽셀 밀도에 비례하므로 원경처럼 작게 보이는 대상에 유리 |
| `C2 → C3`에서 BasePass 드로우 콜이 크게 감소 | 인스턴싱의 본래 효과 |
| `C4 → C5`의 개선폭은 작음 | HLOD가 이미 대체한 액터에 컬 거리는 중복 |
| 간판(`S0/S1`)에서는 Nanite가 불리 | 마스크드·반투명은 Nanite의 약점 |
| 매우 단순한 지오메트리에서는 비Nanite가 우세할 수 있음 | Nanite는 고정 오버헤드가 있다 |

마지막 항목이 중요하다. **Nanite가 지는 결과가 나와도 그대로 기록한다.**
"어떤 조건에서 어느 쪽이 유리한가"가 이 실험의 결론이고, 한쪽 편을 드는 것이 아니다.
