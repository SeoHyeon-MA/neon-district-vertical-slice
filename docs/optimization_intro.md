# 원경 최적화 입문 — 지금까지 만든 것과 그 이유

언리얼을 처음 켜 본 사람 기준으로, `Lvl_NeonDistrict`에 무엇을 만들었고 그것이 왜 필요한지를 처음부터 설명합니다. 용어를 이미 안다고 가정하지 않습니다.

> 작업할 때 참조하는 규칙집은 [level_workflow.md](level_workflow.md)입니다. 이 문서는 그 규칙이 왜 그렇게 정해졌는지를 설명하는 해설서입니다.
> 다이어그램이 포함된 웹 버전은 [optimization_intro.html](optimization_intro.html)에 있습니다.

| | |
|---|---|
| Project | Neon District |
| Map | `Lvl_NeonDistrict` |

## 01. 왜 배경이 문제인가

### 화면 한 장에 쓸 수 있는 시간은 16.6밀리초다

게임은 1초에 60장의 그림을 새로 그립니다. 그러면 한 장에 허용된 시간은 **1초 ÷ 60 = 약 16.6밀리초**입니다. 이 시간 안에 캐릭터 이동, 총알 판정, 적 AI 판단, 그리고 화면 그리기까지 전부 끝나야 합니다. 넘어가면 프레임이 떨어지고 화면이 끊깁니다. 최적화란 결국 **이 16.6밀리초를 어디에 쓸지 정하는 일**입니다.

### 범인 1 — 물체의 개수

화면에 물체 하나를 그리려면 CPU가 그래픽카드에게 이렇게 말합니다. "이 모양을, 이 재질로, 여기에 그려줘." 이 **부탁 한 번**을 드로우 콜(Draw Call)이라고 합니다.

문제는 부탁하는 행위 자체에 비용이 든다는 점입니다. 건물이 500채면 부탁을 500번 넘게 해야 하고, 그래픽카드가 아무리 좋아도 부탁을 만들어내는 CPU가 먼저 지칩니다. 그래서 도시 배경에서는 **폴리곤이 몇 개인지보다 물체가 몇 개인지가 더 중요합니다.**

### 범인 2 — 그림자를 만드는 조명

조명이 그림자를 만들려면 엔진은 그 조명의 시점에서 장면을 **한 번 더** 그려봐야 합니다. 무엇이 무엇에 가려지는지 알아야 하니까요. 사이버펑크 씬은 네온 간판이 수백 개인데, 간판마다 조명을 달면 화면을 수백 번 다시 그리는 셈이 됩니다.

그래서 이 프로젝트에는 규칙이 하나 있습니다. **원경의 창문 불빛과 네온은 조명이 아니라 "스스로 빛나는 색"으로 칠한다.** 멀리서 보면 똑같아 보이지만 비용은 0에 가깝습니다.

### 그래서 원경은 특별하게 다룬다

플레이어가 실제로 걸어 다닐 수 있는 공간은 150m × 150m 한 구역뿐입니다. 그 바깥의 도시는 **보이기만 하면 되고, 만질 일이 없습니다.** 만질 일이 없다는 건 문을 열 필요도, 벽에 부딪힐 필요도, 안으로 들어갈 필요도 없다는 뜻입니다.

## 02. 링 구조 — 거리를 다섯 개의 띠로 자른다

"멀리 있는 건 대충 만든다"는 말은 작업 지침이 되지 못합니다. 얼마나 멀면 대충인지, 대충이 정확히 무엇인지 정해져 있지 않으니까요. 그래서 거리를 다섯 개의 띠(Ring)로 자르고, 띠마다 무엇을 넣고 무엇을 넣지 않을지를 미리 못 박았습니다.

```text
 PLAYER
   ●   ▄▄  ▄▄▄ ▄▄  │ ▄▄▄  ▄▄  ▄  │ ▄▄▄▄  ▄▄  ▄▄▄▄▄ │  ▓▓▓▓  ▓▓▓  ▓▓▓▓▓ │  ~~~~~~~~
───┴───────────────┴─────────────┴────────────────┴──────────────────┴───────────
   Ring 0            Ring 0.5      Ring 1            Ring 2             Ring 3
   0 – 150 m         ~300 m        300 m – 1 km      1.5 – 4 km         4 km +
   충돌 O · 조명 O    겉면만        충돌 X · 조명 X     실루엣만            안개 · 대기
   걸어다닐 수 있음    들어갈 수 없음  반복 건물 재사용    덩어리로 합침        지오메트리 없음
```

멀어질수록 오브젝트는 차례로 잃습니다. 먼저 충돌과 내비게이션, 그다음 조명과 재질의 디테일, 마지막에는 개별성 자체(여러 개가 한 덩어리로 합쳐짐).

| Ring | 거리 | 충돌 | 내비 | 텍스처 | 조명 액터 |
|---|---|---|---|---|---|
| Ring 0 | 0–150 m | 있음 | 있음 | 2K | 있음 (그림자 일부) |
| Ring 0.5 | ~300 m | 단순 박스 | 없음 | 1K | 발광 재질만 |
| Ring 1 | 300 m–1 km | 없음 | 없음 | 512 | 없음 |
| Ring 2 | 1.5–4 km | 없음 | 없음 | 256 | 없음 |
| Ring 3 | 4 km + | — | — | — | — |

이 표가 있으면 나중에 "이 건물에 콜리전을 넣어야 하나?" 같은 질문에 매번 고민하지 않아도 됩니다. 링만 확인하면 답이 나옵니다.

## 03. 언리얼 용어

| 용어 | 뜻 |
|---|---|
| 액터 Actor | 레벨에 놓인 모든 것. 건물, 조명, 카메라, 플레이어 시작 지점까지 전부 액터입니다. |
| 스태틱 메시 | 움직이지 않는 3D 모양 덩어리. 건물, 벽, 상자가 여기 해당합니다. |
| 머티리얼 | 표면의 재질. 색, 반사, 발광을 정의합니다. 원경의 네온 창문은 여기서 처리합니다. |
| 레벨 (맵) | 하나의 공간 파일. 우리 맵은 `Lvl_NeonDistrict` 입니다. |
| World Partition | 맵을 격자로 잘라 **플레이어 근처만 메모리에 올리는** 자동 스트리밍 시스템. |
| LOD | Level of Detail. 같은 물체의 **거칠게 만든 버전**을 미리 준비해 두고 멀어지면 바꿔 끼웁니다. |
| HLOD | Hierarchical LOD. 멀리 있는 **여러 물체를 하나로 합친** 대역 배우. 이 프로젝트의 핵심입니다. |
| 컬링 Culling | 화면 밖이거나 너무 멀거나 가려진 것을 **아예 그리지 않고 건너뛰는** 것. |
| 인스턴싱 ISM | 똑같은 모양이 여러 개일 때 모양 정보는 한 번만 보내고 위치만 여러 개 보내는 방식. |
| Data Layer | 액터들을 묶어 한꺼번에 켜고 끄는 **스위치**. |
| Nanite | UE5의 자동 지오메트리 처리 기술. LOD를 손으로 만들지 않아도 알아서 단순화합니다. 만능은 아닙니다. |
| Lumen | UE5의 실시간 조명·반사 시스템. 젖은 노면 반사가 예쁜 대신 비쌉니다. |

## 04. 지금 맵에 있는 것

현재 맵에 놓인 것은 전부 **회색 상자**입니다. 이 단계를 블록아웃(그레이박스)이라고 부릅니다. 예쁜 건물을 먼저 만들지 않는 이유는 단순합니다. 건물을 다 만든 뒤에 "골목이 너무 좁네" 하고 깨달으면 만든 걸 전부 버려야 하기 때문입니다. **공간과 거리를 먼저 확정하고, 그 위에 아트를 얹습니다.**

| 이름 | 개수 | 정체 | 왜 필요한가 |
|---|---|---|---|
| `BLK_Ground_PlayArea` | 1 | 150m × 150m 지면 | 플레이어가 서 있을 바닥. 윗면이 높이 0의 기준선입니다. |
| `BLK_Boundary_N/S/E/W` | 4 | 높이 30m 경계벽 | 플레이 구역의 끝을 눈으로 보이게 합니다. 나중에 이 자리에 건물 파사드가 들어섭니다. |
| `REF_Gauge_*` | 3 | 100 / 150 / 200cm 기준물 | 사람 크기의 자. 아래 설명 참조. |
| `DIST_R1_00–11` | 12 | Ring 1 스텁 블록 | 450–670m 거리의 중경 도시. 지금은 상자, 나중에 건물 키트로 교체. |
| `DIST_R2_00–07` | 8 | Ring 2 스텁 블록 | 1.5–2.6km 거리의 스카이라인. 높이 250–500m. |
| `CAM_Perf_01–05` | 5 | 성능 측정용 고정 카메라 | 매번 똑같은 자리에서 측정하기 위한 삼각대. |

### 스케일 게이지 — 사람 크기의 자

3D 공간에는 원근이 있어서 눈으로는 크기를 못 잡습니다. 그래서 플레이어 시작 지점 옆에 정확한 치수의 상자 세 개를 세워 뒀습니다.

- **100cm** — 웅크려 숨는 엄폐물의 높이
- **150cm** — 서서 숨는 엄폐물의 높이
- **200cm** — 사람이 지나갈 수 있는 문 폭

골목을 만들 때 이 상자 옆에 대 보면 "좁다/넓다"가 감이 아니라 숫자로 판단됩니다.

### 원경이 진짜 건물이 아니라 상자인 이유

세 가지입니다. 첫째, **실루엣이 도시의 인상을 결정**하기 때문에 실루엣부터 맞춰야 합니다. 둘째, 상자 20개만 있어도 **지금 당장 성능을 측정**할 수 있어서 나중에 비교할 기준값이 생깁니다. 셋째, 상자는 언제든 버릴 수 있습니다.

### 태그와 폴더

배치할 때 액터마다 `Ring0` `Ring05` `ScaleRef` `Distant_Ring1` `Distant_Ring2` `PerfCam` 같은 **태그**를 붙여 뒀습니다. 태그는 액터에 붙이는 이름표입니다. 이게 있으면 나중에 "Ring 2에 속한 것 전부 골라서 설정 바꿔"가 한 번에 됩니다. 실제로 HLOD 지정도 태그로 8개를 한꺼번에 처리했습니다.

## 05. HLOD — 멀리 있는 여러 개를 하나로 합친다

이 프로젝트에서 가장 중요한 기술입니다. 원리는 **대역 배우**와 같습니다. 멀어서 얼굴이 안 보이는 장면이라면 주연 배우 12명을 부를 필요 없이, 비슷하게 생긴 덩어리 하나로 대신하면 됩니다.

```text
HLOD 없음                              HLOD 적용

▄ ▄ ▄ ▄ ▄ ▄ ▄ ▄ ▄ ▄ ▄ ▄                ███████████████
건물 12개 · 각각 따로                    프록시 1개 · 12개를 합침
 \ \ \ | | | / / / / /                        |
  \ \ \| | |/ / / / /                         |
   [ 드로우 콜 12회 ]                    [ 드로우 콜 1회 ]
        ↓                                     ↓
      [ GPU ]                              [ GPU ]
```

바뀌는 것은 화살표의 개수뿐입니다. 화면에 보이는 결과는 거의 같지만, CPU가 그래픽카드에게 부탁하는 횟수가 12분의 1로 줄어듭니다. 실제 도시 규모에서는 이 비율이 수백 대 1이 됩니다.

### 합치는 방법은 두 가지

**MeshMerge (Ring 1에 사용)** — 여러 건물을 한 덩어리로 붙이기만 합니다. 모양과 재질은 그대로 남아서 꽤 가까이서 봐도 티가 안 납니다. 대신 폴리곤은 줄지 않습니다. 450–670m 거리라 아직 형태가 보이는 Ring 1에 맞습니다.

**MeshSimplify (Ring 2에 사용)** — 합치면서 모양 자체를 뭉갭니다. 창문 턱이나 난간 같은 디테일이 사라지고 실루엣만 남습니다. 1.5–2.6km 거리에서는 어차피 안 보이므로 손해가 없습니다.

| 대상 | 개수 | HLOD 레이어 | 방식 |
|---|---|---|---|
| `Distant_Ring1` | 12 | `HLOD_Ring1_Merged` | MeshMerge |
| `Distant_Ring2` | 8 | `HLOD_Ring2_Simplified` | MeshSimplify |

> **함정 — 이름은 맞는데 설정이 다를 수 있다**
> `HLOD_Ring2_Simplified`의 방식이 이름과 달리 기본값인 Instancing으로 남아 있었습니다. 그대로 두면 Ring 2가 합쳐지지 않아서, 정작 측정할 때 Ring 1과 Ring 2의 차이가 나오지 않습니다. 에셋을 만들 때 이름만 바꾸고 안의 설정을 안 바꾸는 것은 흔한 실수입니다.

**아직 HLOD를 빌드하지 않았습니다.** 빌드란 엔진이 실제로 합친 덩어리를 계산해 만들어 두는 작업입니다. 이건 의도된 순서입니다. 먼저 HLOD 없는 상태의 숫자를 재 두고, 그다음 빌드해서 다시 재야 "얼마나 좋아졌는지"를 말할 수 있기 때문입니다.

## 06. 데이터 레이어 — 액터를 묶어서 끄고 켜는 스위치

맵의 액터를 그룹으로 묶고, 그룹 전체를 한 번에 켜고 끌 수 있게 하는 기능입니다. 방마다 조명 스위치를 따로 두는 것과 같습니다.

이걸 만든 이유는 두 가지입니다. 첫째, **측정할 때 원인을 분리**하기 위해서입니다. 프레임이 떨어질 때 원경 스위치만 꺼 보면 원경 때문인지 아닌지 바로 알 수 있습니다. 둘째, 나중에 아트가 들어오면 **회색 상자 블록아웃을 통째로 끄고** 진짜 건물만 볼 수 있습니다.

| 레이어 | 액터 | 담는 것 |
|---|---|---|
| `DL_Blockout` | 8 | 지면, 경계벽 4개, 스케일 게이지 3개 |
| `DL_Distant` | 20 | Ring 1 · Ring 2 원경 블록 전부 |
| `DL_Gameplay` | 1 | 플레이어 시작 지점 (앞으로 NPC, 적, 트리거) |
| `DL_Art_Ring0` | 0 | 아직 비어 있음 — 플레이 구역의 실제 아트 |

측정용 카메라 5개는 **일부러 어느 레이어에도 넣지 않았습니다.** 스위치를 껐다 켜는 실험 도중에 측정 기준점이 사라지면 안 되기 때문입니다.

> **함정 1 — Editor 타입에 바닥을 넣으면 안 된다**
> 데이터 레이어에는 Editor 타입과 Runtime 타입이 있습니다. Editor 타입은 에디터에서만 존재하고 실제 게임 빌드에는 포함되지 않습니다. 처음에 블록아웃 레이어를 Editor로 만들었는데, 그대로 두면 게임을 실행했을 때 바닥이 통째로 사라져 플레이어가 허공으로 떨어집니다. Runtime으로 바꿨습니다. Editor 타입은 주석이나 참조 마커처럼 플레이어가 절대 만나지 않는 보조 물건에만 씁니다.

> **함정 2 — 기본값이 "꺼짐"이다**
> 레이어를 등록하면 `Initial Runtime State`가 기본적으로 Unloaded(안 불러옴)로 설정됩니다. 이 상태로 게임을 실행하면 해당 레이어의 액터가 아예 로드되지 않습니다. 네 레이어 모두 Activated로 바꿔야 정상적으로 보입니다. 원경 기여도를 측정할 때만 `DL_Distant`를 잠시 Unloaded로 되돌립니다.

## 07. 측정 — 숫자가 없으면 최적화가 아니라 기분이다

"HLOD를 켜니까 빨라진 것 같다"는 포트폴리오에서 아무 의미가 없습니다. **몇 밀리초에서 몇 밀리초가 됐는지**가 있어야 합니다. 그래서 아트를 만들기 전에 측정 체계부터 세웠습니다.

### 고정 카메라 5개

측정은 매번 완전히 똑같은 조건에서 해야 비교가 됩니다. 손으로 카메라를 움직여 재면 각도가 조금만 달라져도 숫자가 흔들립니다.

| 카메라 | 보는 것 | 이 시점을 고른 이유 |
|---|---|---|
| `01 StreetEntrance` | 거리 진입부 | 원경이 가장 넓게 열리는 최악의 각도 |
| `02 AlleyInterior` | 골목 내부 | 원경이 가려진 상태. 비교용 기준선 |
| `03 Hideout2FWindow` | 적 건물 2층 창 | 실내 + 창밖 원경이 동시에 보이는 조합 |
| `04 CombatZone` | 전투 구역 중앙 | AI와 이펙트가 함께 도는 실제 플레이 상황 |
| `05 SkylineOverlook` | 상공 40m | 원경 부하만 순수하게 보는 시점 |

### 무엇을 적는가

게임 실행 중 콘솔(물결표 키)에 명령을 입력하면 화면에 숫자가 표시됩니다.

| 명령 | 보이는 것 | 의미 |
|---|---|---|
| `stat unit` | Frame / Game / Draw / GPU | 한 장을 그리는 데 걸린 밀리초. Draw가 크면 CPU가, GPU가 크면 그래픽카드가 병목입니다. |
| `stat rhi` | DrawPrimitive calls | 앞에서 설명한 "부탁 횟수". 단, Nanite를 쓰면 이 숫자가 거의 움직이지 않습니다 — 08장을 참고하세요. |
| `stat scenerendering` | Mesh draw calls | 화면에 실제로 그려진 물체의 수. |
| `ProfileGPU` | 구간별 비용 | 그림자, 조명, 반사 중 무엇이 비싼지 항목별로 보여줍니다. |
| `wp.Runtime.HLOD 0 / 1` | HLOD 끄기 / 켜기 | 같은 자리에서 껐다 켜며 재면 그대로 전후 비교표가 됩니다. |
| `r.Nanite 0 / 1` | Nanite 끄기 / 켜기 | Nanite가 실제로 이득인지 확인합니다. 항상 이득은 아닙니다. |

자세한 측정 조건은 [perf/README.md](perf/README.md), 기록 양식은 [perf/_template.md](perf/_template.md)를 따릅니다.

### 측정의 유일한 규칙

**한 번에 하나만 바꾼다.** HLOD를 켜면서 동시에 텍스처 해상도를 낮추면, 좋아진 이유가 둘 중 무엇인지 영영 알 수 없습니다. 하나 바꾸고, 재고, 기록하고, 커밋합니다.

## 08. 첫 측정 결과 — 숫자를 읽는 법

2026-09-02에 Phase 0 기준선을 실제로 쟀습니다. 전체 수치는 [perf/baseline.md](perf/baseline.md)에 있고, 여기서는 **그 숫자가 무슨 뜻인지**를 설명합니다.

### 한 장을 그리는 데 세 명이 동시에 일한다

그림 한 장은 세 단계를 거치는데, 이 셋은 순서대로가 아니라 **동시에** 일합니다. 조립 라인과 같아서 **가장 느린 사람의 속도가 전체 속도**가 됩니다. 이 느린 사람을 병목이라고 부릅니다.

| 이름 | 하는 일 | 비유 | 우리 수치 |
|---|---|---|---|
| Game | 게임 로직. AI 판단, 총알 이동, 충돌 검사 | 기획자 | 2.1 ms |
| Render | "이걸 이렇게 그려라"라고 GPU에 지시서를 씀 | 작업 지시자 | 12.4 ms |
| GPU | 실제로 픽셀을 칠함 | 공장 | 11.4 ms |

Render가 12.4ms인 것은 지시자가 바빠서가 아니라 **공장이 밀려서 기다리고 있기 때문**입니다. 주문을 넣었는데 공장이 안 받아주니 서서 대기하는 상태입니다.

즉 이 프로젝트는 **GPU 바운드**입니다. 기획자(Game)는 2.1ms만 쓰고 놀고 있습니다. 그래서 지금 AI 코드를 아무리 잘 짜도 프레임은 1도 빨라지지 않습니다. 손댈 곳은 조명, 그림자, 화면에 보이는 물체 — 그리는 쪽입니다.

### 측정 결과

| 카메라 | Frame | Game | Render | GPU | FPS | Draw Calls |
|---|---:|---:|---:|---:|---:|---:|
| 01 StreetEntrance | 12.42 ms | 2.13 | 12.40 | 11.43 | 80.5 | 23 |
| 02 AlleyInterior | 12.40 ms | 2.09 | 12.39 | 11.42 | 80.6 | 23 |
| 03 Hideout2FWindow | 12.84 ms | 2.12 | 12.82 | 11.84 | 77.9 | 23 |
| 04 CombatZone | 12.68 ms | 2.10 | 12.66 | 11.68 | 78.9 | 23 |
| 05 SkylineOverlook | 13.42 ms | 2.11 | 13.41 | 12.39 | 74.5 | 23 |

RTX 3060 Ti / Ryzen 5 5600X, Standalone 1920×1080. 카메라당 5000프레임을 캡처해 로딩 구간을 제외한 마지막 2500프레임의 평균입니다.

### 이 표가 말하는 세 가지

**첫째, 카메라를 바꿔도 1ms밖에 차이나지 않습니다.**
원경이 전혀 안 보이는 골목(12.40ms)과 도시 전체가 보이는 상공(13.42ms)의 차이가 1.02ms입니다. 지금 원경 스텁 20개가 만드는 부하는 프레임의 8%도 안 됩니다.

**둘째, 나머지 11.4ms는 화면에 뭐가 있든 나가는 고정비입니다.**
가게로 치면 손님이 0명이어도 나가는 월세입니다. 켜져 있는 기능들이 물체 단위가 아니라 **화면 전체**에 대해 계산하기 때문입니다.

- Lumen(실시간 간접광): 빛이 벽에 튕기는 걸 매 프레임 계산합니다. 물체가 없어도 하늘빛이 바닥에 반사되는 계산은 돕니다.
- Virtual Shadow Maps(고품질 그림자): 드로우 콜 23장 중 13.6장을 그림자가 씁니다. 가장 큰 몫입니다.
- SkyAtmosphere와 볼류메트릭 안개: 화면 전체 픽셀에 걸립니다.

**이 고정비를 알아둔 것이 기준선의 진짜 값어치입니다.** 나중에 GPU가 25ms로 나오면 "25ms구나"가 아니라 **"콘텐츠가 13.6ms를 먹고 있구나"** 라고 읽을 수 있습니다. 뺄 기준이 없으면 이 분해가 불가능합니다.

**셋째, 드로우 콜은 이 구성에서 지표가 되지 못합니다.**
어느 카메라에서든 23으로 똑같고, 그중 실제 물체를 그리는 몫(BasePass)은 1.9장뿐입니다. 템플릿의 `SM_Cube`가 **Nanite** 메시이기 때문입니다.

Nanite는 물체를 하나씩 주문받는 대신 화면 전체를 한 번에 훑어서 지금 보이는 픽셀에 필요한 만큼만 알아서 그립니다. 공장이 주문서를 안 받고 자동으로 처리하는 신형 라인이 깔린 셈입니다. 그래서 건물이 20채든 2000채든 주문서 수가 늘지 않습니다.

### 그래서 정해야 할 것

앞의 06장에서 설명한 HLOD, 인스턴싱, 컬링은 전부 **주문서 수를 줄이는** 기법입니다. Nanite를 쓰는 한 그 숫자가 애초에 안 움직이므로, "Draw Calls 500 → 50" 같은 표는 만들 수 없습니다. 두 갈래 중 하나를 골라야 합니다.

| | A안 — Nanite 유지 | B안 — Nanite 끈 버전도 함께 제작 |
|---|---|---|
| 비교 지표 | GPU 시간만 | GPU 시간 + 드로우 콜 |
| 작업량 | 기본 | 원경을 두 벌 만들어야 함 |
| 보여지는 것 | 현대적 워크플로우 | 두 방식의 차이를 수치로 아는 사람 |

TA 직군 포트폴리오라면 B안이 훨씬 강합니다. "왜 이 방식을 골랐는가"에 근거를 댈 수 있기 때문입니다. 다만 Phase 3에서 진짜 도시를 만든 뒤에 결정해도 늦지 않습니다.

### 앞으로 어떤 그림이 나와야 성공인가

```
지금 (스텁 큐브 20개)        GPU 11.4ms   고정비만
    ↓ Phase 3 · 진짜 도시 배치
최적화 전                    GPU 26ms     콘텐츠가 14.6ms. 프레임 붕괴
    ↓ Phase 4 · HLOD / 컬링 / 라이트 예산을 하나씩
최적화 후                    GPU 15ms     콘텐츠 3.6ms. 11ms 절약
```

숫자는 예시입니다. 이 표가 나오면 "동일 카메라·동일 설정에서 GPU 시간을 26ms에서 15ms로 42% 줄였고, 그중 HLOD가 7ms, 컬링이 2ms, 라이트 예산이 2ms를 기여했다"고 말할 수 있습니다. **기법별 기여도를 쪼갤 수 있다는 것**이 핵심이고, 그래서 최적화를 몰아서 하지 않고 하나씩 적용하며 매번 재는 것입니다.

### 지금 수치의 한계

스텁은 머티리얼 한 장짜리 단순 상자입니다. 실제 키트로 바꾸면 GPU 시간이 크게 오릅니다. 따라서 **최적화 효과를 증명하는 실질적 기준선은 Phase 3 직후에 다시 잡아야 합니다.** 지금 이 표의 역할은 두 가지입니다 — 측정 파이프라인이 재현 가능하게 돈다는 확인, 그리고 빈 상태의 고정비를 알아두는 것.

## 10. 왜 이 순서인가

이 프로젝트에서는 **순서 자체가 결과물**입니다. 최적화 과정을 수치로 보여주는 게 목표이므로, 재기 전에 고쳐 버리면 보여줄 것이 없습니다.

| Phase | 하는 일 | 끝나는 조건 |
|---|---|---|
| 0 · 기준선 | 측정 환경 고정, 5개 카메라 수치 기록 | 비교할 숫자가 문서에 남았을 때 |
| 1 · 그레이박스 | 상자만으로 150m 동선 완성, 전투 테스트 | 동선을 더 안 고치겠다고 결정했을 때 |
| 2 · 키트 | 건물 모듈 6–8종과 마스터 머티리얼 제작 | 같은 조각으로 도시가 만들어질 때 |
| 3 · 원경 | 스텁을 실제 키트로 교체, 안개와 실루엣 조정 | 최적화 전 수치를 다시 쟀을 때 |
| 4 · 최적화 | 스트리밍, HLOD, Nanite, 컬링, 라이트 예산 | 항목마다 전후 수치가 기록됐을 때 |
| 5 · 폴리싱 | 네온 라이팅, 포스트, 최종 재측정 | 최종 비교표가 완성됐을 때 |

Phase 4의 항목들은 한 번에 하나씩 적용하고 매번 커밋합니다. 그러면 저장소의 커밋 기록 자체가 **"무엇을 해서 몇 ms를 줄였다"의 연대기**가 됩니다.
